# RFC-001: Women Experts Roster Platform

## Decision
Use a TypeScript monorepo with a Next.js web client, NestJS REST API, PostgreSQL persistence through Prisma, Docker for local reproducibility, and GitHub Actions for verification.

## Request flow

```text
Browser → Next.js web app → NestJS API → Prisma → PostgreSQL
                                      ↘ Audit event store
```

Public profile reads use an approved-only query. Submission and moderation use separate commands with server-side role checks. The API is the trust boundary; the browser is not trusted to enforce permissions.

## Domain model

- `User`: identity, role, locale, disabled state.
- `ExpertProfile`: bilingual biography, professional category, location, languages, visibility state.
- `Submission`: immutable submission event and review decision.
- `Category`: controlled classification vocabulary.
- `AuditEvent`: actor, action, entity, timestamp, and safe metadata.

## API shape

- `GET /health`
- `GET /api/v1/categories`
- `GET /api/v1/experts?query=&category=&location=&language=` — approved records only
- `POST /api/v1/submissions` — authenticated expert
- `GET /api/v1/admin/submissions` — reviewer/admin
- `POST /api/v1/admin/submissions/:id/approve` — reviewer/admin
- `POST /api/v1/admin/submissions/:id/reject` — reviewer/admin

## Alternatives considered

A server-rendered single application would reduce deployment units but make the API boundary less explicit for future integrations. A document database would simplify early schema changes but is less appropriate for controlled categories, relational moderation history, and reporting.

## Risks

The largest risks are privacy mistakes, incomplete Arabic UX, and untested authorization edges. Mitigations are approved-only query scopes, field-level response DTOs, RTL acceptance tests, and permission-focused integration tests.
